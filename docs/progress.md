## Completed
- Foundation, menu, inventory, procurement, PO generation, and H-1 cancellation implemented.
- Procurement stock check uses material-stock row locking and active stock reservations.
- One procurement request per scheduled menu and one PO per procurement request are enforced.
- PO ordered quantity is server-controlled from verified net procurement.
- H-1 cancellation reserves replacement stock before cancelling a PO item.
- `migrations/000006_create_receiving.sql` added.
- Receiving tables added: `receipts`, `receipt_items`, `receipt_documents`.
- Receipt item quantity may be zero to record a vendor visit where an item was not delivered (`NOT_RECEIVED`).
- Multiple receipts per PO item are supported.
- Cumulative vendor receipt quantity is calculated from all receipt rows for a PO item.
- Receipt item status is recalculated cumulatively as `NOT_RECEIVED`, `PARTIAL_RECEIVED`, `RECEIVED`, or `OVER_RECEIVED`.
- Receipt quantity and agreed PO price are persisted separately; `actual_amount` is generated by PostgreSQL as received quantity × agreed unit price.
- Positive receipt quantity creates a stock `IN` movement with reference type `PO_RECEIPT` and increases `material_stocks` in the same transaction.
- Zero receipt quantity records the receipt/status but does not create a stock movement.
- Receiving locks the PO item before cumulative calculations, serializing concurrent receipts for the same item.
- PO header receipt status is recalculated as `VERIFIED`, `PARTIALLY_RECEIVED`, or `COMPLETED` from item statuses.
- Receipt document metadata supports `INVOICE`, `NOTA`, `PHOTO`, and `OTHER`.
- Receiving HTTP routes are wired in `cmd/api/main.go`.

## Important Implementation Notes
- Authentication is not implemented; audit user IDs such as `verified_by`, `cancelled_by`, and `received_by` temporarily come from request bodies where required.
- Persisted quantities/prices use PostgreSQL `NUMERIC`; JSON quantity/price inputs are strings to avoid floating-point precision loss.
- Receiving derives material, unit, and agreed price from the PO item. The client only supplies PO item ID and actual received quantity, preventing receipt data from silently changing the deal.
- `actual_amount` is generated by PostgreSQL and cannot be supplied by the client.
- Receipt documents currently store metadata/path/URL only. File-object storage/upload infrastructure is intentionally separate.
- H-1 date evaluation uses `Asia/Jakarta` business time.

## Latest Decisions
- Vendor is not master data; supplier/source is per transaction/item.
- Fixed agreed unit price does not change at receipt.
- Multiple vendor receipts are cumulative per PO item.
- A zero-quantity receipt is a valid operational record and maps to `NOT_RECEIVED`; it does not create inventory movement.
- Over-delivery is determined from cumulative vendor receipt quantity.
- Every positive receipt quantity enters stock immediately and atomically with its receipt record.
- Gross requirement is not overwritten by net procurement.
- Stock reservation is allocation only, not a stock movement.
- GitHub Actions is the canonical executable validation environment.
